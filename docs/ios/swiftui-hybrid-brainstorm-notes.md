# SwiftUI hybrid shell — running brainstorm notes

Working notes for an in-progress design session. NOT a spec yet. The spec, once
agreed, goes to `docs/superpowers/specs/`.

## Why this came up

Phase 3.1 shipped to Ash's iPhone and the verdict was blunt: the app still looks
"absolutely horrible" on iPhone. Fair — 3.1 was survival plumbing (data loss,
keyboard, safe area, autocorrect, onboarding, updater), not visual design. The
adaptive UI was Phases 3.2–3.5 and none of it is built.

Two 3.1 changes made things visibly WORSE and are pending revert:
- the 44px touch floor + `flex-wrap` turned the zoom toolbar into a vertical
  column (and at 100% a 4-row block) floating over the résumé
- the `visualViewport` `--app-height` work distorts the layout when the keyboard
  opens — composer flies to the top with a black void beneath it

Settings on iPhone wraps one word per line, clips the Dark toggle, and overlaps
its own Replay button. It is a two-column desktop dialog on a 390pt screen.

## Hard constraint that frames everything

**The résumé canvas must stay HTML.** Vector PDF export hands WKWebView's
`createPDF` the *live app DOM* — the "HTML renders both screen and PDF"
architecture. Rebuilding the résumé in SwiftUI means a second rendering engine
for PDF, and the two drift on every layout change.

## Decisions so far

1. **SwiftUI owns the full native shell.** Not just modals — a real navigation
   bar, toolbar and sheet structure, hosting the webview as a child view that
   shows only the résumé page. Keyboard avoidance then comes free and the
   `visualViewport` hack goes away entirely.
2. **The web keeps editing.** The webview renders the résumé AND keeps
   tap-to-edit contentEditable exactly as today — already verified working on
   real hardware, caret and selection included. SwiftUI owns everything outside
   the page. This keeps ONE editing implementation and a small bridge.

## Open: where the Xcode project lives

`src-tauri/gen/` is **entirely gitignored — zero files tracked**, and is
regenerated by `tauri ios init`. A full native shell needs to own the root view
controller, which the generated app entry point owns today. Options:

- **Commit `gen/apple`** — treat the Xcode project as source. Supported, but
  inherits merge conflicts on generated files.
- **Drive it from Rust** — precedent exists: `src-tauri/src/ios_view.rs` already
  uses objc2 to fix the `UIWindow` tao leaves without a `windowScene`. Tracked,
  survives regeneration.
- **A Tauri plugin's Swift package** — tracked and regeneration-proof (this is
  how `tauri-plugin-dialog` ships `DialogPlugin.swift`), but plugins are built
  for commands, not for owning the view hierarchy. Probably insufficient here.
- **Drop Tauri on iOS entirely** — a native Swift app embedding the résumé
  renderer bundle in a plain WKWebView. Avoids fighting the generated project,
  but reimplements storage, and the shared asset becomes the *renderer* rather
  than the app.

## Standing cost to keep stating plainly

Every piece of chrome exists twice — SwiftUI on iOS, React on Mac/Windows.
Settings changes get built twice. That is the actual decision; feasibility is
not in doubt.

## Consequence

Phases 3.2–3.5 as specced are largely wrong — they all assume a web shell.

3. **The JS store stays source of truth.** appStorage / the Rust disk store
   stays authoritative; SwiftUI holds no durable state and reads/writes through
   the bridge. One data layer, one backup format, frozen `resume-designer-*`
   keys untouched, iOS and desktop identical below the UI.

## CloudKit — settled, and it is NOT a reason to move data into Swift

"Source of truth for the running app" and "who owns the sync engine" are
different questions. Storage is already one file per key written by Rust
(atomic tmp+rename), and the same Rust store runs on iOS — so a native Swift
CloudKit layer can replicate those files and signal the app to reload, with the
JS store still authoritative while the app is open.

**The real tension is unrelated to SwiftUI.** The decision on record is
documents-only sync with PER-VARIANT CloudKit records, but `resume-designer-data`
is a SINGLE key holding EVERY variant. At file granularity the whole library is
one record: edit résumé A on the Mac and résumé B on the phone and they collide
with no merge path. Two futures, both independent of this design:
  - sync the blob — simple, last-writer-wins across the whole library
  - split storage so each variant is its own key/file — matches sync
    granularity, but touches BACKUP_FIXED_KEYS, the backup format and profile
    namespacing
That split is needed whichever UI ships. Doing it in Swift would mean
reimplementing the store AND diverging iOS from desktop at the storage layer.

4. **Commit `src-tauri/gen/apple` and own the entry point.** Un-ignore the
   Xcode project, treat it as real source, and replace the generated SwiftUI
   entry point with ours: it builds the shell and hosts Tauri's webview as a
   child view. Keeps Tauri's commands, storage and updater intact, and stops
   `tauri ios init` silently reverting the shell. Accepted cost: a generated
   project becomes a maintained one, so Tauri upgrades bring conflicts we own.
   NOTE: this means changing `resume-designer/.gitignore:10` (`src-tauri/gen/`)
   to ignore only the non-Apple targets.

5. **Structure panel is native SwiftUI** (not the web editor in a native sheet).
   This KILLS the "document never crosses the bridge" rule — accepted knowingly.
   It is what makes SwiftUI chrome a project rather than a refactor: Settings and
   onboarding are forms, the structure panel is a synchronised editor.

6. **Bridge shape: snapshot-in, path-writes-out, with a focus rule.**
   - Read: structured JSON snapshot of the document, pushed to Swift on change
   - Write: setField(path, value) + moveItem / addItem / removeItem
   - REUSES the existing path grammar (`experience[3].bullets[1]`,
     `sections[2].title`) already exercised by changeApply.js, the diff engine
     and every applied AI edit. Do NOT invent a parallel grammar.
   - Swift never owns a document TYPE — it renders a snapshot and writes paths.
     The JS store stays the single writer, so canvas and panel cannot diverge.

## Three named risks on the structure-panel bridge

1. ECHO WHILE TYPING — Swift sets field -> store updates -> snapshot pushes
   back -> SwiftUI re-renders the field being typed in, cursor jumps. RULE: a
   focused native field ignores inbound snapshots for its own path until blur.
2. SNAPSHOT GRANULARITY — whole-document JSON per keystroke is wasteful (a real
   résumé is ~8 roles x 5 bullets). Start debounced, measure before optimising.
3. PATH GRAMMAR DRIFT — if SwiftUI builds paths itself it becomes a second
   implementation of a grammar whose drift has already caused data corruption.
   Swift must echo back paths it RECEIVED, never construct them.

## BLOCKER found executing step 1 (2026-08-10) — the spec's premise is wrong

`find src-tauri/gen/apple -type f` = 33 source files (plus build/Externals).
The ENTIRE generated app entry point is `Sources/resume-designer/main.mm`:

    #include "bindings/bindings.h"
    int main(int argc, char * argv[]) {
        ffi::start_app();
        return 0;
    }

There is NO SwiftUI, NO AppDelegate, NO SceneDelegate and NO view controller in
the generated project. wry/tao build the whole UI hierarchy from Rust, and
`ffi::start_app()` owns the application lifecycle and the run loop. (This is
also why `src-tauri/src/ios_view.rs` has to reach in via objc2 to fix the
UIWindow — there is no Swift layer to do it from.)

So spec decision 1 ("SwiftUI owns the full native shell and hosts the webview as
a child view") is NOT a matter of replacing a generated entry point. It requires
INVERTING who owns the application lifecycle. SwiftUI's `App` wants the run
loop; tao wants the run loop.

Three ways forward, needing a decision before any more code:

A. TAO KEEPS THE LIFECYCLE; SwiftUI is injected into the hierarchy.
   Write SwiftUI in Swift files in the committed Xcode project, expose them as
   @objc classes, and have Rust instantiate/attach them via objc2 — extending
   the ios_view.rs pattern. Keeps Tauri whole. Cost: the shell is assembled
   from Rust through objc2, chrome<->webview layout is hand-wired, and SwiftUI
   never owns navigation. Least native of the three.

B. SWIFT OWNS THE LIFECYCLE; link the Rust lib, skip tao's app bootstrap.
   Replace main.mm with a Swift @main App, do not call ffi::start_app(), and
   create the WKWebView ourselves — then hand it to Tauri, or run Tauri's IPC
   without its windowing. Most native result. Cost: leaves Tauri's supported
   path for iOS; every Tauri upgrade risks breaking the seam. Needs a spike to
   find out whether Tauri's iOS plumbing can be driven without start_app().

C. NATIVE iOS APP, Tauri desktop-only (the option rejected earlier, now cheaper
   by comparison). Swift owns everything; the shared asset is the RENDERER
   bundle, not the app. Storage moves to Swift, contradicting decision 3.

Note this also reopens the gen/apple decision: if B or C, committing Tauri's
generated project may be pointless.
